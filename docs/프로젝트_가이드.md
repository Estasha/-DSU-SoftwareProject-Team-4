# 동네 진단 서비스 — 프로젝트 가이드 (팀 공유용)

> 이 문서는 프로젝트 기획부터 기술 스택, 데이터 수집, 협업 방식까지 결정된 내용을 정리한 것입니다.
> 팀원들이 AI(Claude, ChatGPT 등)에게 질문할 때 이 문서를 프롬프트에 붙여넣으면, 매번 프로젝트 맥락을 설명하지 않아도 바로 이어서 도움을 받을 수 있습니다.

## 1. 프로젝트 개요

**주제**: 동네 진단 — 자취방 구하기 전 "우리 동네 성적표" 서비스

**문제의식**
부동산 앱(직방·다방 등)은 시세·매물 정보만 제공하고, 실제 거주자가 체감하는 안전·생활편의·교통 접근성 같은 정보는 흩어져 있어 "살아보기 전엔 알 수 없다"는 문제가 있음.

**목표**
주소 하나만 입력하면 해당 지역의 안전·생활편의·교통 접근성을 종합 점수화해서 보여주는 리포트 서비스 제공.

**기존 서비스와의 차별점**
| 구분 | 기존 부동산 앱 | 동네 진단 |
|---|---|---|
| 제공 정보 | 시세, 매물 사진 | 안전·생활편의·교통 종합 점수 |
| 데이터 성격 | 거래 정보 | 공공데이터 기반 정주 여건 |
| 의사결정 시점 | 매물 선택 이후 | 지역 선택 이전 사전 진단 |

**기존 서비스의 문제점 (상세)**
- 안전 관련 정보는 행정안전부 "안전디딤돌" 등 별도의 공공 안전 포털에서만 확인 가능하며, 치안안전·범죄주의구간 데이터가 지도 위에 표시되긴 하나 부동산 정보와는 전혀 연동되어 있지 않음. 이용자가 특정 매물이나 동네를 검색할 때 이 데이터를 함께 참고할 방법이 없음
- 다방·직방 등 주요 부동산 플랫폼은 매물 위치, 가격, 방 구조 등 거래 조건 검색에 최적화되어 있으며, 지도 화면에도 매물 클러스터 수·가격 정보만 표시될 뿐 안전성이나 지역 생활권 전반에 대한 지표는 제공하지 않음
- 일부 플랫폼(예: 다방)은 특정 매물 상세페이지에서 "주변 생활시설" 도보 거리(지하철역·마트·약국·편의점 등)를 보여주기도 하나, 이는 이미 선택한 개별 매물 단위로만 제공되는 부가 정보에 그침. 여러 지역을 종합 점수로 비교하거나 안전 지표와 결합해서 볼 수 있는 기능은 없음 — 즉 매물을 고르고 난 "사후 확인" 수준에 머물러 있어, 애초에 어느 동네를 선택할지 판단하는 "사전 진단" 단계에서는 활용 불가
- 결과적으로 이용자는 부동산 앱에서 매물 조건을 비교하고, 별도로 공공 안전 포털에 접속해 치안 정보를 다시 확인하는 등 여러 서비스를 오가며 정보를 직접 취합해야 하는 불편을 감수하고 있으며, 이 과정에서 생활편의·교통 접근성까지 포함한 종합적 판단은 사실상 이루어지기 어려움

**실제 주거 선정의 근거 — 왜 안전·생활편의·교통이 중요한가**
- 한국보건사회연구원의 「인구이동과 정주여건」 연구(실제 이주 시 의향 결정 조건 분석)에 따르면, 생필품 구매·주택환경과 관련된 생활 인프라와 범죄·재난으로부터의 안전과 관련된 안전 인프라가 지역 정주를 결정하는 핵심 요인으로 나타남. 두 인프라에 대한 만족도가 낮을수록 타 지역으로의 이주 의향이 크게 높아지는 것으로 분석됨. 다만 도보 5분(400m) 이내에 이러한 생활 인프라가 완전히 갖춰진 경우는 41.8%에 그쳐, 지역 간 격차가 상당함을 시사함
  - (참고: 인프라는 생활 인프라, 안전 인프라 외에 대중교통·공공서비스 수준을 의미하는 '기초 인프라'까지 총 4종이 존재하나, 기초 인프라는 현재 기준으로 지역별 편차가 크지 않고 이주 의향에 미치는 영향도 특정 수치를 넘기면 제한적으로 작아짐)
- 주택 입지 결정요인에 관한 선행연구에서도 입지조건이 주택구입 결정요소 중 가장 큰 비중(28%)을 차지했으며, 세부적으로는 교통편리(26.4%)·편의시설(20.0%) 등이 상위 요인으로 나타나, 안전·생활편의·교통이 부수적 정보가 아니라 거주지 선택의 핵심 변수임이 뒷받침됨
- 이는 대학생·사회초년생뿐 아니라 신혼부부, 이직·전근에 따른 이주자 등 거주지를 새로 탐색하는 모든 수요자에게 공통적으로 적용되는 판단 기준이라는 점에서, 본 서비스가 특정 세대에 국한되지 않는 보편적 문제를 다루고 있음을 보여줌
  - 참고 기사: https://www.khan.co.kr/article/202605251438001/

**수요처의 개선 요구 및 시장 변화 대비**
- 1인 가구 및 청년층의 자취·독립 수요가 지속적으로 증가하면서, 매물 조건뿐 아니라 지역 자체의 정주 여건을 사전에 비교·판단하려는 수요가 커지고 있음
- 공공데이터 개방이 확대됨에 따라 이를 실생활 의사결정에 접목한 서비스에 대한 정책적·시장적 요구가 높아지고 있으나, 현재까지는 안전·생활편의·교통 정보가 각기 다른 서비스에 파편화되어 있을 뿐, 이를 하나의 지표로 통합해 "지역 단위 사전 비교"를 지원하는 서비스는 부재함

**개발 필요성 (종합)**
"동네 진단" 서비스는 기존 부동산 서비스와 공공 안전 포털이 각각 따로 제공하던 정보를 하나의 종합 점수 체계로 통합하고, 매물 선택 이전 단계에서 지역 자체를 진단할 수 있도록 함으로써 정보 비대칭을 해소하고 수요자의 합리적 의사결정을 지원하는 것을 목적으로 함.

**플랫폼**: 웹 (앱이 아닌 이유 — 위치기반 네이티브 기능이 필수가 아니고, 배포·테스트가 간단해 학기 프로젝트 일정에 유리. 필요 시 PWA로 확장 가능)

## 2. 활용 데이터 및 출처

1차 버전은 데이터 품질과 자동 수집 가능성이 검증된 **3개 지표**로 스코프를 한정함. (생활소음 지표는 구·군 단위 공개 데이터 부재로 1차 범위에서 제외)

| 지표 | 데이터셋 | 출처 | 형태 | 수집 난이도 |
|---|---|---|---|---|
| 안전 | 경찰서별 5대 범죄 발생 현황 | 공공데이터포털(data.go.kr) | CSV | 낮음 |
| 생활편의 | 소상공인시장진흥공단_상가업소정보 | 공공데이터포털(data.go.kr) | CSV/API | 낮음 |
| 생활편의(보조) | 병원정보서비스 | 건강보험심사평가원(HIRA), data.go.kr에 등록 | API | 낮음~중간 |
| 교통 접근성 | 버스정류장·지하철역 위치 | 부산 Big-데이터웨이브(data.busan.go.kr), 국가대중교통정보센터(TAGO) | CSV/API | 낮음~중간 |
| 주소→좌표 변환 | 지오코딩 | 카카오맵 API | API | 중간 (호출량 관리 필요) |

> 안전 지표는 GIS 공간분석이 필요한 생활안전지도(safemap.go.kr) WMS 데이터 대신, 구 단위 집계가 바로 가능한 경찰서별 범죄 통계 CSV를 채택해 구현 난이도를 낮춤.

## 3. 사용자 요구사항 분석표

프로젝트에서 구현해야 할 기능(FR)과 품질 기준(NFR)을 정리한 표입니다. 별도 파일로도 제공됩니다 — `동네진단_사용자요구사항분석표.xlsx`

| ID | 구분 | 요구사항명 | 상세 설명 | 관련 사용자 | 우선순위 | 수용 기준 |
|---|---|---|---|---|---|---|
| FR-01 | 기능 | 주소 검색 | 사용자가 텍스트로 주소를 입력하면 좌표로 변환 | 전체 사용자 | 상 | 유효 주소 입력 시 좌표 반환 성공 |
| FR-02 | 기능 | 지역 매칭 | 변환된 좌표를 기준으로 소속 행정동을 판별 | 전체 사용자 | 상 | 좌표 → 동 이름 정확히 매핑 |
| FR-03 | 기능 | 지표별 점수 조회 | 해당 동의 안전·생활편의·교통 점수를 DB에서 조회 | 전체 사용자 | 상 | 3개 지표 값이 모두 정상 반환 |
| FR-04 | 기능 | 종합 점수 계산 | 정규화된 지표를 가중합하여 최종 점수 산출 | 전체 사용자 | 상 | 계산식대로 0~100 사이 값 산출 |
| FR-05 | 기능 | 리포트 시각화 | 점수를 카드/레이더차트 형태로 화면에 표시 | 전체 사용자 | 중 | 점수 변경 시 화면에 즉시 반영 |
| FR-06 | 기능 | 지도 표시 | 검색 위치를 카카오맵에 마커로 표시 | 전체 사용자 | 중 | 마커가 정확한 위치에 렌더링됨 |
| NFR-01 | 비기능 | 응답 속도 | 검색 후 결과 표시까지 3초 이내 | 전체 사용자 | 중 | 3초 초과 시 로딩 UI라도 표시 |
| NFR-02 | 비기능 | 데이터 최신성 | 공공데이터는 최소 연 1회 갱신 | 데이터 담당 | 하 | 갱신 스크립트 재실행으로 반영 가능 |
| NFR-03 | 비기능 | 브라우저 호환성 | 크롬·사파리 등 주요 브라우저에서 정상 동작 | 전체 사용자 | 중 | 2개 이상 브라우저에서 QA 통과 |
| NFR-04 | 비기능 | API 키 보안 | 카카오·공공데이터 키가 프론트에 노출되지 않음 | 개발팀 | 상 | 브라우저 개발자도구에서 키 미노출 확인 |

**용어**
- **기능(FR)**: 시스템이 "무엇을" 해야 하는지에 대한 요구사항
- **비기능(NFR)**: 시스템이 "얼마나 잘" 동작해야 하는지에 대한 요구사항 (속도, 보안, 호환성 등)

**우선순위 기준**
- **상**: 이게 없으면 서비스가 성립하지 않는 핵심 요구사항
- **중**: 핵심은 아니지만 사용자 경험에 중요한 영향을 주는 요구사항
- **하**: 있으면 좋지만 후순위로 미뤄도 되는 요구사항

## 4. 기술 스택

| 영역 | 기술 | 비고 |
|---|---|---|
| 프론트엔드 | React (Vite) + Tailwind CSS | 컴포넌트 단위 분업에 유리 |
| 시각화/지도 | Recharts, 카카오맵 JavaScript SDK | 점수 차트 및 주소 검색·지도 표시 |
| 백엔드 | Python + FastAPI | 데이터 전처리(pandas)와 언어 통일 |
| 데이터베이스 | Turso (libSQL 클라우드) | 팀원 전체가 하나의 DB 서버 공유 |
| 데이터 전처리 | Python + pandas | 공공데이터 정제 및 점수화 로직 구현 |
| 배포 | 프론트: Vercel/Netlify, 백엔드: Render/Railway | 무료 티어로 학기 프로젝트 충분 |
| 협업 도구 | GitHub, Notion | 이슈·PR 관리, 화면 설계 공유 |

**언어 정리**: Python(백엔드+데이터 전처리) + JavaScript/TypeScript(프론트엔드) + SQL(DB 쿼리, ORM 사용 시 최소화 가능)

**데이터 처리 파이프라인**
```
공공데이터(CSV/API) → Python/pandas 전처리 & 점수화 → Turso(libSQL) 적재
→ FastAPI REST API → React 프론트엔드 조회 및 시각화
```

## 5. API 키 발급 가이드

### ① 공공데이터포털 (data.go.kr)
경찰서 범죄통계, 상가업소정보, 병원정보, 버스정류장 데이터 전부 여기서 발급.
1. www.data.go.kr 회원가입
2. "데이터셋" 메뉴에서 원하는 데이터셋 검색 → "활용신청"
3. 대부분 자동승인, 일부는 심사(2~3일) 소요
4. 마이페이지 > "오픈API" > "개발계정"에서 인증키 확인
5. **인증키는 1인당 1개, 모든 data.go.kr API에 공통 사용** — 데이터 담당자 1명이 대표로 신청해 팀과 공유

> 위치기반서비스사업자 신고 안내가 뜨는 경우: 실시간으로 움직이는 대상(예: 실시간 버스 위치)의 위치정보 API에서만 해당. 우리 프로젝트가 쓰는 정적 시설 위치 데이터는 대부분 해당 없음. 애매하면 "해당없음" 옵션 확인 또는 고객센터(1566-0025) 문의.

### ② 부산 Big-데이터웨이브 (data.busan.go.kr)
별도 회원가입 후 데이터셋 페이지에서 활용신청.

### ③ 카카오맵 API (지오코딩용)
1. developers.kakao.com 로그인
2. "내 애플리케이션" > "애플리케이션 추가하기"
3. 앱 키 중 **REST API 키** 사용 (지오코딩용)
4. "플랫폼" 메뉴에서 사용 도메인 등록 필수 (로컬: `http://localhost:포트`)
5. 무료 티어 하루 30만 건 — 팀 프로젝트 규모엔 충분

### 공통 주의사항
- API 키는 `.env` 파일에 저장, `.gitignore`로 Git 업로드 방지
- `.env.example`(빈 값 템플릿)만 Git에 올리고, 실제 키는 노션 비공개 페이지 등으로 공유

## 6. 프론트엔드란

**한 줄 정의**: 사용자가 브라우저 화면에서 직접 보고 클릭하는 모든 부분. "이 서비스가 어떻게 생겼나"를 만드는 영역.

**우리 프로젝트에서 프론트엔드가 하는 일**
- 주소를 입력하는 검색창 화면
- "검색" 버튼을 누르면 백엔드에 요청을 보내고, 응답으로 받은 점수 데이터를 화면에 표시
- 안전·편의·교통 점수를 카드나 레이더 차트 같은 시각적 형태로 보여줌
- 카카오맵으로 지도 위에 위치를 표시

**React를 쓰는 이유**
- 화면을 "컴포넌트"라는 작은 조각으로 나눠서 만들 수 있음 (예: 검색창 컴포넌트, 점수 카드 컴포넌트, 지도 컴포넌트) — 각자 따로 만들어서 조립하는 방식이라 팀 작업에 유리
- 데이터가 바뀌면 화면이 자동으로 갱신됨 (예: 새 주소를 검색하면 점수 카드 내용이 자동으로 바뀜)

**동작 흐름 예시**
```
사용자가 주소 입력 → "검색" 버튼 클릭
  → 프론트엔드가 백엔드 API에 요청 전송 (예: GET /api/score?address=...)
  → 백엔드가 계산한 점수(JSON 형태)를 응답으로 받음
  → 받은 데이터를 화면에 카드/차트로 렌더링
```

**프론트엔드 담당자가 다루는 주요 파일**
- `.jsx`(또는 `.tsx`) 파일 — 화면 구성 요소(컴포넌트) 코드
- API 요청 코드 (`fetch`나 `axios`로 백엔드에 데이터 요청)
- 스타일링 (Tailwind CSS 클래스로 디자인 적용)

### 이 프로젝트에서 쓰는 프론트엔드 기술 상세

**① React — 화면을 만드는 핵심 라이브러리**

"화면을 작은 조각(컴포넌트)으로 나눠서 조립하는" 방식으로 UI를 만드는 JavaScript 라이브러리.

- 예: `SearchBar`(주소 검색창), `ScoreCard`(점수 카드), `MapView`(지도)처럼 화면을 부품 단위로 쪼갤 수 있음
- 각 부품은 재사용 가능 — "점수 카드"를 안전/편의/교통 3번 다르게 재사용하는 식
- 데이터가 바뀌면 화면이 자동으로 갱신됨 — 새 주소를 검색하면 점수 값(데이터)만 바꿔주면 화면(카드)이 알아서 다시 그려짐. 직접 "이 텍스트를 지우고 새로 써라"라고 명령할 필요 없음

**컴포넌트 코드 예시**
```jsx
function ScoreCard({ title, score }) {
  return (
    <div className="p-4 rounded-lg shadow">
      <h3>{title}</h3>
      <p className="text-2xl">{score}점</p>
    </div>
  );
}

// 사용할 때
<ScoreCard title="안전 점수" score={72} />
<ScoreCard title="교통 점수" score={85} />
```
`{title}`, `{score}`는 **props**라고 불리는데, "이 부품에 넣어주는 값"이라고 생각하면 됨. 같은 카드 틀에 다른 값만 넣어서 재사용하는 것.

**② Vite — React 프로젝트를 빠르게 세팅/실행해주는 도구**

- React 코드를 브라우저가 이해할 수 있는 형태로 변환하고, 실행 중 코드를 고치면 화면에 바로 반영해주는(새로고침 없이) 개발 서버 역할
- 예전엔 이런 역할을 하는 도구로 Webpack이 많이 쓰였는데, Vite가 훨씬 빠르고 설정이 간단해서 요즘 신규 프로젝트엔 거의 Vite를 씀
- 실제로 팀원이 하는 건 딱 한 줄: `npm create vite@latest` 치면 기본 뼈대가 자동으로 만들어짐

**③ Tailwind CSS — 디자인(스타일) 입히는 도구**

- CSS 파일을 따로 만들어서 "이 클래스는 이런 색, 이런 크기"를 정의하는 대신, HTML 태그에 미리 정해진 클래스 이름을 바로 붙여서 스타일을 줌
- 위 코드 예시의 `className="p-4 rounded-lg shadow"`가 그것 — `p-4`(padding), `rounded-lg`(둥근 모서리), `shadow`(그림자)를 조합만 하면 됨
- 장점: CSS 파일을 따로 왔다갔다 안 해도 되고, 정해진 값 안에서 고르는 거라 디자인이 들쭉날쭉해지는 걸 막아줌

**④ Recharts — 점수를 차트로 보여주는 라이브러리**

- 안전/편의/교통 점수를 레이더 차트(육각형처럼 생긴 차트)나 막대 그래프로 시각화할 때 씀
- React 컴포넌트 형태로 되어 있어서 데이터만 넣어주면 차트가 그려짐
```jsx
<RadarChart data={[
  { subject: '안전', value: 72 },
  { subject: '편의', value: 65 },
  { subject: '교통', value: 80 },
]}>
  ...
</RadarChart>
```

**⑤ 카카오맵 JavaScript SDK — 지도 표시**

- 검색한 주소 위치를 실제 지도 위에 마커로 찍어서 보여줄 때 사용
- 카카오 디벨로퍼스에서 받은 REST API 키(지오코딩용)와는 별개로, 지도를 "화면에 그리는" 용도로는 **JavaScript 키**를 따로 써야 함 (앞서 발급받은 앱 안에 두 종류 키가 같이 들어있음)

**전체적으로 어떻게 맞물리나**

```
Vite로 프로젝트 뼈대 생성
  → React로 컴포넌트(SearchBar, ScoreCard, MapView) 조립
  → Tailwind로 각 컴포넌트에 스타일 입힘
  → Recharts로 점수 시각화
  → 카카오맵 SDK로 지도 표시
  → 백엔드 API 호출해서 실제 데이터 받아와 위 컴포넌트들에 꽂아넣음
```

정리하면 **Vite = 개발 환경, React = 화면 구조, Tailwind = 디자인, Recharts/카카오맵 = 특수 기능(차트·지도)**로 역할이 나뉘어 있다고 보면 됨.

## 7. 백엔드란

**한 줄 정의**: 사용자 눈에는 안 보이지만, 실제 로직을 처리하고 데이터베이스와 대화하는 "서버 쪽" 프로그램.

**비유**: 식당으로 치면, 프론트엔드는 손님이 보는 메뉴판·테이블이고, 백엔드는 주방(주문받아 실제로 요리하는 곳), 데이터베이스는 재료를 보관하는 창고.

**우리 프로젝트에서 백엔드가 하는 일**
1. **API 서버 만들기** — 프론트엔드가 요청을 보낼 수 있는 창구(엔드포인트) 제공
   ```
   GET /api/score?address=부산광역시 해운대구 우동
   ```
2. **요청 처리 로직**
   - 주소를 카카오 지오코딩 API로 좌표로 변환
   - 그 좌표가 속한 동을 DB에서 조회
   - 해당 동의 안전·편의·교통 점수를 DB에서 꺼내옴
   - 가중치 공식으로 최종 점수 계산
   - 결과를 JSON 형태로 프론트엔드에 반환
3. **데이터베이스와 소통** — SQL(또는 ORM)로 DB를 조회·가공
4. **외부 API 연동 관리** — 카카오맵, 공공데이터포털 API 호출을 서버 쪽에서 대신 처리 (API 키를 프론트에 노출하지 않기 위한 보안 목적)
5. **에러 처리** — 존재하지 않는 주소 입력, API 호출 실패 등 예외 상황 처리

**코드 예시 (FastAPI)**
```python
@app.get("/api/score")
def get_score(address: str):
    lat, lng = geocode(address)                          # 1. 주소 → 좌표
    region = find_region_by_coord(lat, lng)               # 2. 좌표 → 동 찾기
    safety = db.query(SafetyScore).filter_by(region_id=region.id).first()
    facility = db.query(FacilityScore).filter_by(region_id=region.id).first()
    final_score = safety.score * 0.4 + facility.score * 0.6   # 3. 가중합
    return {"region": region.name, "final_score": final_score}
```

**정리**: 백엔드는 "사용자 요청 → 데이터 조회 → 계산 → 응답"이라는 흐름을 코드로 만드는 역할. 데이터 담당이 정리해둔 재료를, 프론트엔드가 요청할 때마다 꺼내고 계산해서 내어주는 역할.

### 이 프로젝트에서 쓰는 백엔드 기술 상세 (6개)

**① FastAPI — API를 만드는 틀**
```python
@app.get("/api/score")
def get_score(address: str):
    return {"address": address, "score": 72}
```
`@app.get("/api/score")`는 "이 주소로 요청이 오면 아래 함수를 실행해라"는 뜻. `address: str`는 프론트엔드가 보낸 값을 자동으로 받아주고 타입까지 검사해줌. 함수가 반환하는 값은 자동으로 JSON으로 변환됨. (요청/응답 형태 검증은 FastAPI에 기본 내장돼 있어서 따로 배울 필요 없음)

**② Uvicorn — 서버를 실제로 켜는 실행 명령어**
```bash
uvicorn main:app --reload
```
FastAPI로 짠 코드를 "항상 요청을 기다리는 서버"로 돌려주는 프로그램. `--reload`는 코드 수정 시 자동 재시작(개발 중에만 사용).

**③ SQLAlchemy — Turso(DB) 조회**
```python
region = db.query(Region).filter(Region.name == "해운대동").first()
```
SQL 문법을 직접 안 쓰고 파이썬 코드로 DB를 조회·수정할 수 있게 해주는 도구.

**④ requests — 카카오 지오코딩·공공데이터 API 호출**
```python
res = requests.get(url, headers=headers, params={"query": address})
```
공공데이터포털, 카카오 지오코딩처럼 다른 서버의 API를 우리 백엔드가 대신 호출할 때 사용. 프론트엔드가 직접 호출하면 API 키가 브라우저에 노출되는 보안 문제가 있어서, 백엔드가 중간에서 대신 호출해주는 구조.

**⑤ python-dotenv — `.env`에 저장한 API 키 불러오기**
```python
load_dotenv()
KAKAO_API_KEY = os.getenv("KAKAO_API_KEY")
```
API 키를 코드에 직접 하드코딩하지 않고 `.env` 파일에서 불러와서 사용.

**⑥ CORS 설정 — 프론트(포트 다름)와 백엔드 통신 허용**
```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_methods=["*"],
    allow_headers=["*"],
)
```
프론트(예: `localhost:5173`)와 백엔드(예: `localhost:8000`)가 다른 포트에서 돌면 브라우저가 기본적으로 요청을 막는데, 이 설정으로 허용해줌. 배포 후에는 실제 프론트엔드 도메인(Vercel 주소)을 등록해야 함.

**전체 흐름**
```
Uvicorn이 FastAPI 서버 실행
  → 프론트엔드 요청이 CORS 통과 후 도착
  → requests로 카카오 지오코딩 API 호출 (주소→좌표)
  → SQLAlchemy로 Turso에서 점수 조회
  → 계산된 결과를 JSON으로 프론트엔드에 응답
```

**참고**: DB 마이그레이션 도구(Alembic)나 별도 연결 드라이버(sqlalchemy-libsql)도 있지만, 학기 프로젝트 규모에서는 `Base.metadata.create_all()` 한 줄로 테이블을 만들면 충분하고, sqlalchemy-libsql은 SQLAlchemy가 내부적으로 쓰는 부품이라 직접 다룰 일이 없어 위 6개에서 제외함.

## 8. 데이터베이스 기초 개념 (팀 전체 참고용)

- **테이블 = 엑셀 시트**. 행(row)은 데이터 하나, 열(column)은 속성.
- **기본키(Primary Key)**: 각 행을 구분하는 고유 번호 (`id`)
- **외래키(Foreign Key)**: 다른 테이블의 id를 참조해서 테이블끼리 연결 (관계형 데이터베이스)
- **SQL**: DB에 말 거는 언어. 핵심 4동사 — `INSERT`(넣기), `SELECT`(조회), `UPDATE`(수정), `DELETE`(삭제)
- **ORM(SQLAlchemy 등)**: SQL 문법 대신 파이썬 코드로 DB를 다룰 수 있게 해주는 도구
- **마이그레이션(Migration)**: DB 테이블 구조 변경을 코드 파일로 기록 → Git으로 버전관리 → 팀원 전체가 같은 구조로 동기화 (Alembic 사용)
- **PostgreSQL vs SQLite**: SQLite는 파일 하나가 곧 DB (가벼움, 서버 프로세스 불필요). PostgreSQL은 항상 켜져 있는 서버 프로세스로, 접속해서 SQL로 요청해야 함
- **Turso**: SQLite와 호환되는 libSQL을 클라우드에서 서버처럼 제공하는 서비스. 로컬에 DB 서버를 따로 설치할 필요 없이, 팀원 전체가 같은 클라우드 DB에 접속하므로 동기화 문제가 원천적으로 없음 (SQLite 파일을 각자 컴퓨터에 따로 두는 방식과 달리, Turso는 하나의 DB를 클라우드에서 공유). Python에서 연결하려면 `sqlalchemy-libsql`, `sqlalchemy` 같은 연결 라이브러리만 설치하면 됨

**추천 실습**: SQLBolt(sqlbolt.com)로 기본 SQL 1~2시간 연습 → Turso 무료 프로젝트 생성해서 실전 연결

## 9. 데이터 전처리란 & 흐름 (예시 코드)

**데이터 전처리란**
공공데이터 CSV를 받아보면 바로 쓸 수 없는 경우가 대부분입니다. 경찰서 이름 표기가 제각각이거나("부산해운대경찰서" vs "해운대경찰서"), 빈 칸(결측치)이 있거나, 숫자가 문자로 저장돼 있거나, 우리가 원하는 "동" 단위가 아니라 "경찰서 관할구역" 단위로 되어 있는 식입니다. 이걸 그대로 DB에 넣으면 점수 계산이 틀어지기 때문에, 넣기 전에 미리 다듬는 작업이 필요합니다. 이를 **데이터 전처리**라고 합니다.

**pandas란**
pandas는 Python에서 표(테이블) 형태의 데이터를 다루기 위한 라이브러리입니다. CSV 파일을 열면 엑셀처럼 행과 열로 이루어진 표가 되는데, pandas는 이 표를 **DataFrame**이라는 객체로 불러와서 코드로 조작할 수 있게 해줍니다.

- `pd.read_csv("파일명.csv")` — CSV 파일을 DataFrame으로 불러오기
- `df.head()` — 위에서 5줄만 미리 보기 (데이터가 어떻게 생겼는지 확인용)
- `df["컬럼명"]` — 특정 열(컬럼) 하나만 선택
- `df["컬럼명"].fillna(0)` — 빈 값을 0으로 채우기
- `df.merge(다른df, on="공통컬럼명")` — 두 표를 공통 값 기준으로 합치기 (엑셀의 VLOOKUP과 비슷)

즉, 엑셀에서 마우스로 하던 필터링·정렬·병합·계산 작업을 코드 몇 줄로 자동화할 수 있게 해주는 도구입니다. 데이터가 수백 건이면 엑셀로도 되지만, 공공데이터처럼 수만~수십만 건이 되면 pandas 같은 도구가 사실상 필수입니다. 연도가 바뀌어 새 CSV가 나와도, 같은 스크립트를 다시 돌리기만 하면 되는 것도 큰 장점입니다.

**보통 거치는 단계**
1. **수집(Load)** — CSV 파일을 읽어오거나 API로 데이터를 받아옴
2. **정제(Cleaning)** — 표기 통일, 불필요한 열 제거, 이상값 걸러내기
3. **결측치 처리** — 빈 값이 있는 행을 지울지, 채울지 결정
4. **타입 변환** — 문자열로 된 숫자를 실제 숫자(int/float)로 변환
5. **매핑/집계** — 경찰서 관할구역 → 행정동처럼, 원하는 단위로 재집계
6. **정규화(Normalization)** — 절대값(예: 범죄건수)을 비교 가능한 0~100점 점수로 변환

**예시 코드**
```python
import pandas as pd

# 1. 수집
df = pd.read_csv("경찰서별_5대범죄_2024.csv", encoding="cp949")

# 2. 정제
df.columns = df.columns.str.strip()
df["경찰서명"] = df["경찰서명"].str.replace("부산", "").str.strip()

# 3. 결측치 처리
df = df.fillna(0)

# 4. 타입 변환
df["총범죄건수"] = df["총범죄건수"].astype(int)

# 5. 매핑 (경찰서 관할구역 → 행정동, 팀이 직접 만든 기준표 사용)
mapping = pd.read_csv("경찰서_동_매핑표.csv")
df = df.merge(mapping, on="경찰서명")

# 6. 정규화 (0~100점, 범죄가 적을수록 높은 점수)
min_v, max_v = df["총범죄건수"].min(), df["총범죄건수"].max()
df["안전점수"] = 100 - ((df["총범죄건수"] - min_v) / (max_v - min_v) * 100)
```

**까다로운 지점**
- 경찰서 관할구역 ↔ 행정동 경계 불일치 → 팀이 직접 매핑 기준표 작성 필요
- 여러 지표(범죄·편의시설·교통)의 정규화 기준을 통일해야 가중합이 의미 있어짐

## 10. 배포란

**한 줄 정의**: 내 컴퓨터에서만 돌아가던 서비스를, 인터넷 어디서나 다른 사람도 접속할 수 있게 서버에 올리는 작업.

**왜 필요한가**
지금까지 개발한 코드는 각자 컴퓨터의 `localhost`(내 컴퓨터 안에서만 접속 가능한 주소)에서만 실행돼요. 교수님이나 청중에게 보여주려면, 이걸 **인터넷에 상시 켜져 있는 서버**로 옮겨야 누구나 URL 하나로 접속할 수 있어요. 이 과정을 배포(Deploy)라고 합니다.

**우리 프로젝트의 배포 구조**
| 영역 | 배포처 | 이유 |
|---|---|---|
| 프론트엔드 (React) | Vercel 또는 Netlify | 정적 파일(HTML/CSS/JS)을 올리는 서비스. GitHub 저장소만 연결하면 자동 배포됨. 무료 |
| 백엔드 (FastAPI) | Render 또는 Railway | 항상 켜져 있어야 하는 서버 프로그램을 대신 실행해주는 서비스. 무료 티어 제공 |
| 데이터베이스 | Turso | 이미 클라우드에 있으므로 별도 배포 불필요 |

**대략적인 흐름**
1. GitHub 저장소를 Vercel(프론트)과 Render(백엔드)에 각각 "연결"
2. 두 서비스 모두 **환경변수(Environment Variables)** 설정 화면에서 `.env`에 있던 API 키들을 그대로 등록 (카카오 키, 공공데이터 키, DB 접속 정보 등) — 이렇게 해야 배포된 서버도 로컬과 동일하게 API 호출 가능
3. GitHub의 `main` 브랜치에 새 커밋이 올라올 때마다 Vercel/Render가 **자동으로 재배포**함 (별도 명령어 없이 push만 하면 반영됨)
4. 배포 완료 후 각 서비스가 제공하는 고유 URL(예: `https://dongne-jindan.vercel.app`)로 실제 접속 확인

**왜 이 조합을 쓰나 (초보자 관점)**
- 서버를 직접 사서 설정하는 것보다 훨씬 간단함 — 코드만 올리면 알아서 실행 환경을 만들어줌
- 무료 티어로 학기 프로젝트 규모는 충분히 커버됨
- GitHub와 연동되어 있어서, 앞서 설명한 GitHub 워크플로우(브랜치 → PR → main 머지)가 그대로 배포 파이프라인이 됨

**주의할 점**
- 무료 티어는 일정 시간 요청이 없으면 서버가 "잠들었다가" 첫 요청 시 다시 깨어나는 데 몇 초~수십 초 걸릴 수 있음 (발표 직전엔 미리 한 번 접속해서 깨워두는 걸 추천)
- 로컬에서는 잘 되는데 배포 후 안 되는 경우, 대부분 **환경변수를 배포 서비스에 등록하는 걸 빠뜨린 경우**이니 가장 먼저 확인

## 12. GitHub 협업 워크플로우

### Git과 GitHub 기초 (처음이라면 먼저 읽기)

**Git과 GitHub은 다른 것**
- **Git**: 내 컴퓨터에 설치해서 쓰는 "버전관리 프로그램". 코드가 바뀔 때마다 스냅샷(기록)을 남겨서, 언제든 예전 상태로 되돌리거나 누가 뭘 바꿨는지 추적할 수 있게 해줌
- **GitHub**: 그 Git 기록을 인터넷에 올려서 팀원들과 공유할 수 있게 해주는 웹 서비스. "Git으로 관리하는 프로젝트를 온라인에 저장하고 협업하는 곳"이라고 보면 됨

비유하면 Git은 "문서 되돌리기(버전 기록) 기능이 있는 폴더"이고, GitHub은 그 폴더를 클라우드에 올려서 여러 명이 같이 보고 수정할 수 있게 한 것.

**꼭 알아야 할 용어 6개**

| 용어 | 뜻 |
|---|---|
| **Repository(저장소, 레포)** | 프로젝트 전체가 들어있는 폴더. GitHub에 올라간 우리 프로젝트 공간 |
| **Clone** | GitHub에 있는 저장소를 내 컴퓨터로 통째로 복사해오는 것 (최초 1회) |
| **Commit(커밋)** | 코드 변경사항의 스냅샷을 남기는 것. "이 시점까지 작업한 걸 기록해둔다"는 의미 |
| **Branch(브랜치)** | 원본 코드를 건드리지 않고 안전하게 실험할 수 있는 "가지". 각자 자기 브랜치에서 작업하고 나중에 합침 |
| **Push** | 내 컴퓨터에 쌓인 커밋들을 GitHub(원격 저장소)로 업로드 |
| **Pull** | GitHub에 있는 최신 변경사항을 내 컴퓨터로 다운로드 |

**설치부터 GitHub 저장소 연결까지 (최초 1회 세팅)**

1. **Git 설치**
   - Windows: https://git-scm.com/downloads 에서 다운로드 후 설치 (설치 옵션은 기본값으로 두고 계속 "Next"만 눌러도 무방)
   - Mac: 터미널에 `git --version` 입력 → 설치 안 돼 있으면 자동으로 설치 안내가 뜸 (또는 `brew install git`)
   - 설치 확인: 터미널(또는 Git Bash)에 아래 명령어를 쳐서 버전이 나오면 성공
     ```
     git --version
     ```

2. **내 신원 등록 (최초 1회)**
   커밋할 때 "누가 이 변경을 했는지" 기록되도록 이름과 이메일을 등록해야 함 (GitHub 계정 이메일과 맞추는 걸 추천)
   ```
   git config --global user.name "이승엽"
   git config --global user.email "본인이메일@example.com"
   ```

3. **GitHub 계정 및 저장소(Repository) 준비**
   - github.com 가입 (팀원 전체 필요)
   - 팀장(또는 담당자 1명)이 저장소 생성: GitHub 우측 상단 `+` 버튼 → `New repository` → 저장소 이름 입력(예: `dongne-jindan`) → `Create repository`
   - 생성 직후 뜨는 화면에서 저장소 주소(URL)를 복사해둠 (예: `https://github.com/팀아이디/dongne-jindan.git`)

4. **팀원들이 저장소를 내 컴퓨터로 가져오기 (Clone)**
   터미널에서 프로젝트를 두고 싶은 폴더로 이동한 뒤:
   ```
   git clone https://github.com/팀아이디/dongne-jindan.git
   ```
   그러면 `dongne-jindan`이라는 폴더가 생기고, 그 안에 GitHub 저장소 내용이 통째로 복사됨. 이후 이 폴더 안에서 작업하면 됨.

5. **이미 로컬에 만들어둔 프로젝트를 나중에 GitHub와 연결하는 경우**
   (팀원이 먼저 로컬에서 코드를 짜기 시작했고, 나중에 GitHub 저장소와 연결하고 싶을 때)
   ```
   cd 내프로젝트폴더
   git init                                                    # 이 폴더를 Git으로 관리 시작
   git remote add origin https://github.com/팀아이디/dongne-jindan.git   # GitHub 저장소 주소 등록
   git add .
   git commit -m "first commit"
   git branch -M main
   git push -u origin main                                     # 최초 push (이후엔 git push만 쳐도 됨)
   ```
   `git remote add origin [주소]`가 핵심입니다 — 내 로컬 폴더에 "이 GitHub 주소가 네 원격 저장소야"라고 알려주는 명령어예요. 한 번 등록해두면 그 다음부터는 `git push`, `git pull`만 쳐도 자동으로 이 주소를 사용합니다.

**가장 기본적인 흐름 (그림으로 이해하기)**

```
[내 컴퓨터]                          [GitHub]
  로컬 저장소  --- push(업로드) --->   원격 저장소
             <--- pull(다운로드) ---
```

1. 처음 딱 한 번: `git clone [저장소주소]` — GitHub 프로젝트를 내 컴퓨터로 복사
2. 코드 수정
3. `git add .` — 수정한 파일을 "커밋할 준비" 상태로 등록
4. `git commit -m "메시지"` — 변경사항을 기록 (스냅샷 생성)
5. `git push` — 내 커밋을 GitHub로 업로드
6. 다른 사람이 작업한 내용을 받고 싶으면 `git pull`

**자주 쓰는 명령어 모음**

| 명령어 | 용도 |
|---|---|
| `git status` | 지금 뭐가 바뀌었고, 뭐가 커밋 준비됐는지 확인 (가장 자주 치게 될 명령어) |
| `git add .` | 바뀐 파일 전체를 커밋 준비 상태로 등록 (특정 파일만: `git add 파일명`) |
| `git commit -m "메시지"` | 스냅샷 기록 |
| `git push` | GitHub로 업로드 |
| `git pull` | GitHub의 최신 내용을 내 컴퓨터로 반영 |
| `git branch` | 지금 로컬에 있는 브랜치 목록 확인 |
| `git checkout -b 브랜치명` | 새 브랜치를 만들고 바로 그 브랜치로 이동 |
| `git checkout 브랜치명` | 이미 있는 다른 브랜치로 이동 |
| `git log` | 지금까지의 커밋 기록(히스토리) 확인 |
| `git clone [주소]` | GitHub 저장소를 내 컴퓨터로 통째로 복사 (최초 1회) |

**왜 브랜치를 나눠서 쓰나**
여러 명이 동시에 같은 코드를 고치면 서로 덮어쓰기 충돌이 나기 쉬워요. 그래서 각자 자기 **브랜치**(가지)를 따로 파서 독립적으로 작업하고, 다 되면 **Pull Request(PR)** 라는 절차를 거쳐 원본(`main` 브랜치)에 합쳐요. PR은 "제 작업물을 검토하고 합쳐주세요"라는 요청이라고 생각하면 됩니다 — 다른 팀원이 코드를 한번 훑어본 뒤 승인해야 합쳐지기 때문에, 이상한 코드가 바로 반영되는 걸 막아주는 안전장치 역할도 해요.

**처음이라면**
명령어(CLI)가 낯설면 **GitHub Desktop** 앱을 깔아서 버튼 클릭으로 clone/commit/push/pull을 할 수 있어요. 위 명령어들을 굳이 외우지 않아도 시작할 수 있습니다.

1. GitHub Projects 칸반보드에서 이슈 확인 및 담당 배정 (To Do → In Progress)
2. `git checkout main && git pull origin main` — 최신 내용 동기화
3. `git checkout -b feature/역할-기능명` — 기능 브랜치 생성
4. 코딩 + 의미 단위로 수시 커밋
5. 로컬에서 직접 테스트 (서버 실행 / 화면 확인)
6. `git push origin feature/...` → GitHub에서 main 대상으로 PR 생성
7. 팀원 1명 리뷰 및 승인(Approve) → main에 머지 → feature 브랜치 삭제
8. 칸반보드에서 Done으로 이동

### 협업 규칙
- PR 템플릿(`.github/PULL_REQUEST_TEMPLATE.md`)으로 "무엇을/어떻게 테스트했는지" 양식 통일
- `.env`, `node_modules/`, `__pycache__/` 등은 반드시 `.gitignore` 등록
- 커밋 메시지 접두어 통일 (`feat:`, `fix:`, `docs:` 등)
- DB 담당자는 실제 데이터가 아니라 **테이블 구조 정의 파일(models.py)과 마이그레이션 파일**을 Git으로 버전관리

## 팀원들이 AI를 활용할 때 사용법

이 문서 전체를 복사해서 ChatGPT나 Claude 등에 붙여넣고, 그 아래에 본인 질문을 이어서 적으면 됩니다.

예시:
```
[이 문서 전체 붙여넣기]

---
위 프로젝트 맥락을 참고해서 답변해줘.

질문: FastAPI에서 위치 좌표로 특정 동을 찾는 함수를 어떻게 짜야 할까?
```

이렇게 하면 프로젝트 배경을 처음부터 다시 설명할 필요 없이, 바로 실질적인 답변을 받을 수 있습니다.
