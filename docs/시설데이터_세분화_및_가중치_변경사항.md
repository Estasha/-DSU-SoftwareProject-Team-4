# 시설 데이터 세분화 및 가중치 표 도입 — 변경 사항과 팀원 할 일

2026-11-15 · 작성: 이승엽 (Estasha)

> 이 문서는 팀원과 팀원이 쓰는 AI 도구가 함께 읽도록 썼습니다. `facilities` 테이블이나
> `data/scripts/clean_facilities.py`를 수정하기 전에 **"6. AI 작업 규칙"**을 먼저 확인해주세요.

## 1. 한 줄 요약

점수 계산(`docs/동네 진단 서비스 정주여건 점수 계산 방식.md`)에서 시설 유형별 가중치를 쓰기 위해
`facilities.facility_type` 값을 세분화했습니다(9종류 → 147종류). 가중치는 DB가 아니라 코드의
표(`backend/app/services/facility_weights.py`)에서 관리합니다. **DB 스키마(컬럼)는 바뀌지 않았고,
시설 목록(어떤 시설이 들어 있는지)도 기존 DB와 똑같습니다.**

## 2. 바뀐 것

### 2-1. `facility_type` 값 세분화

컬럼 구성(`id, category, facility_type, name, latitude, longitude, source`)은 그대로이고,
`facility_type` 값만 바뀌었습니다. 8,315행 중 6,086행이 바뀌었습니다.

| 기존 값 | 행 수 | 새 값 | 방법 |
| --- | --- | --- | --- |
| `소매` | 2,593 | 62종류 (슈퍼마켓, 편의점, 약국 등) | 상가 원본의 업종 소분류(`indsSclsNm`) |
| `음식점` | 3,184 | 42종류 (백반/한정식, 카페 등) | 〃 |
| `문화체육` | 448 | 21종류 (노래방, 당구장 등) | 〃 |
| `병원(HIRA)` | 243 | 17종류 (종합병원, 내과/소아과 의원, 치과의원 등) | 종별 + 병원 이름으로 진료과 판별 |
| `보건의료` | 91 | **그대로** | HIRA 병원과 중복이라 일부러 안 나눔 (아래 참고) |
| `cctv`, `버스정류장`, `지하철역`, `노인교실` | | 그대로 | |

- **상가 목록은 기존 DB 그대로입니다.** 상가 원본을 API로 새로 받으면 폐업하거나 새로 생긴 가게가
  섞이므로, 목록은 기존 `facilities.csv`를 유지하고 원본에서 **같은 가게(같은 상호명·같은 대분류·100m 이내)**를
  찾아 소분류만 붙였습니다. 6,316건 중 5,932건이 매칭됐고, 못 찾은 384건은 기존 값(`소매` 등)을 유지합니다.
- **의원은 이름으로 진료과를 판별했습니다** (`CLINIC_NAME_RULES`). 예: `김내과의원` → `내과/소아과 의원`,
  `화인정형외과의원` → `외과 의원`. 이름에 진료과가 없는 33곳(마취통증의학과, `하나의원` 등)은 `기타 의원`입니다.
- **상가 `보건의료` 91건은 남겨두되 세분화하지 않았습니다.** 같은 병원이 HIRA 데이터에도 있어서
  둘 다 세분화하면 점수가 두 번 들어가기 때문입니다. 가중치 표에 `보건의료`가 없으므로 점수 계산에서
  자동으로 빠지고, 의료 점수는 HIRA 병원만으로 계산됩니다. 지도에는 기존처럼 둘 다 보입니다.

### 2-2. 가중치 표 신설 — `backend/app/services/facility_weights.py`

`facility_type` → `(점수 카테고리, 가중치)` 표입니다. 표에 없는 유형은 점수에서 제외됩니다.

| facility_type | 점수 카테고리 | 가중치 |
| --- | --- | --- |
| `cctv` | 안전 | 1.0 |
| `내과/소아과 의원` | 의료_의원급 | 0.6 |
| `피부/비뇨기과 의원`, `성형외과 의원` | 의료_의원급 | 0.1 |
| `종합병원` | 의료_종합병원 | 1.0 |
| `슈퍼마켓`, `편의점`, `약국` | 생필품 | 1.0 |
| `버스정류장` | 버스 | 1.0 (노선 수는 고려 안 함) |
| `지하철역` | 지하철 | 1.0 |

가중치를 시설 행에 저장하지 않은 이유: 가중치는 아직 초안이라 계속 바뀔 텐데, 행마다 저장하면
값을 바꿀 때마다 DB 전체를 다시 넣어야 합니다. 표로 두면 이 파일 한 줄만 고치면 됩니다.

### 2-3. 수정된 파일

| 파일 | 내용 |

## 3. 현재 상태 (2026-11-15 기준)

| 항목 | 저장소(`facilities.csv`) | Turso DB |
| --- | --- | --- |
| `facility_type` | 세분화된 값 (147종류) | **아직 기존 값 (9종류)** |
| 노인교실 9건 | 있음 | **없음** (CSV에만 추가된 상태) |
| 시설 수 | 8,315 | 8,306 |

이 작업을 한 사람(이승엽)은 Turso DB의 소유자가 아니라서 **DB에는 쓰지 않았습니다**(읽기만 함).
검증은 로컬 SQLite로 했습니다. DB 반영은 아래 4번에서 DB 소유자가 해주셔야 합니다.

## 4. 팀원(DB 소유자)이 해야 할 일

1. 최신 코드 받기: `git pull origin main`
2. (권장) 혹시 모르니 현재 DB 백업. 예: `turso db shell <DB이름> .dump > facilities_backup.sql`
3. `backend` 폴더에서 WSL 가상환경으로 실행:
   ```bash
   python -m app.load_facilities --replace
   ```
   - `facilities` 테이블을 **전부 지우고** `facilities.csv`로 다시 넣습니다. 노인교실 9건도 이때 같이 들어갑니다.
   - `id` 값은 새로 매겨집니다. 현재 `facilities.id`를 참조하는 테이블은 없어서 문제없습니다.
   - `--replace` 없이 실행하면 같은 유형·좌표만 건너뛰기 때문에, 유형 이름이 바뀐 행이 **중복으로 추가됩니다**. 이번에는 반드시 `--replace`를 붙여주세요.
4. 확인: 총 8,315건이고 `facility_type` 종류가 147개면 정상입니다.
   ```sql
   SELECT COUNT(*), COUNT(DISTINCT facility_type) FROM facilities;
   ```

DB 스키마가 바뀌지 않았기 때문에, 위 작업 전이나 후 어느 때 배포(Render)되어도 사이트가 깨지지 않습니다.

## 5. 새 시설 데이터를 추가할 때

1. **`clean_facilities.py`의 `main()`에 블록을 추가합니다.** 기존 블록(예: 노인교실)과 같은 형태로
   `standardize()`를 써서 공통 스키마로 바꿉니다.
2. **`category`는 지도 레이어 4개 중 하나**를 씁니다: `안전` / `생활편의` / `음식점` / `교통`.
   프론트엔드(`frontend/src/pages/SafetyMapPage.jsx`의 `LAYERS`)가 이 값으로 레이어를 나눕니다.
   새 레이어가 필요하면 프론트엔드도 같이 수정해야 합니다.
3. **`facility_type`은 구체적인 유형 이름**으로 정합니다 (예: `어린이집`, `노인복지시설`).
   점수에 반영하려면 `facility_weights.py`의 `FACILITY_WEIGHTS`에 **글자 하나 틀리지 않게 같은 이름**으로
   추가합니다. 표에 없으면 지도에는 보이지만 점수에서는 빠집니다.
4. **이미 있는 데이터와 겹치는지 확인합니다.** 겹치면 한쪽만 점수에 반영되도록, 다른 쪽은 가중치 표에
   없는 `facility_type`으로 둡니다 (상가 `보건의료` 처리 방식 참고).
5. `python data/scripts/clean_facilities.py`로 CSV를 다시 만들고, 4번처럼 `--replace`로 DB에 반영합니다.
   - 원본 CSV(`data/raw/`)는 git에 올라가지 않아서 PC마다 없을 수 있습니다. 원본이 없는 데이터셋은
     기존 `facilities.csv`의 행을 그대로 재사용하므로 지워지지 않습니다. 실행 로그에
     `원본 파일 없음 -> 기존 facilities.csv의 N건 재사용`이 뜨는 건 정상입니다.
   - 실행 후 다른 데이터셋의 건수가 줄지 않았는지 로그를 확인해주세요.

## 6. AI 작업 규칙 (팀원이 쓰는 AI 도구용)

- **가중치를 `facilities` 행에 컬럼으로 저장하지 말 것.** 가중치는 `backend/app/services/facility_weights.py`에서만 관리한다.
- **상가 가게 목록을 API 원본으로 다시 만들지 말 것.** 목록은 기존 `facilities.csv`(= DB)를 유지하고, 원본은 소분류를 붙이는 데만 쓴다(`attach_store_subtypes`). 원본에서 목록을 새로 만들면 DB와 시설 목록이 달라진다.
- **기존 `category` 값(`안전`/`생활편의`/`음식점`/`교통`)을 바꾸지 말 것.** 프론트엔드 지도 레이어가 이 값에 의존한다.
- **`facility_type` 이름을 바꾸면 `FACILITY_WEIGHTS`도 같이 바꿀 것.** 이름이 어긋나면 에러 없이 점수에서 조용히 빠진다.
- **상가 `보건의료`를 세분화하지 말 것.** HIRA 병원과 중복되어 의료 점수가 두 번 들어간다.
- **`facilities` 스키마(컬럼)를 바꿀 때는 Turso DB에 먼저 반영한 뒤 코드를 푸시할 것.** `Base.metadata.create_all`은 이미 있는 테이블에 컬럼을 추가하지 않는다. 배포 서버(Render)도 같은 Turso DB를 쓰므로, 코드만 먼저 올라가면 `no such column` 에러로 배포 사이트의 시설 조회가 깨진다.
- **로컬 테스트는 Turso가 아니라 로컬 SQLite로 할 것.** `DATABASE_URL='sqlite:////tmp/test.db'`를 지정해서 실행하면 `backend/.env`의 Turso 주소보다 우선한다(`load_dotenv`는 이미 설정된 환경변수를 덮어쓰지 않음). `--replace`처럼 데이터를 지우는 명령은 실행 전에 `engine.url`이 SQLite인지 확인한다.
