## 1. 프로젝트 배경 및 필요성

자취방이나 새 거주지를 구할 때, 대부분의 부동산 정보 서비스(직방, 다방 등)는 시세·평형·매물 사진 등 **거래 정보 중심**으로만 구성되어 있다. 그러나 실제로 거주자가 체감하는 삶의 질은 다음과 같은 요소에 크게 좌우된다.

- 동네가 밤늦게 다녀도 안전한가
- 편의점·병원·마트 같은 생활 인프라가 도보권에 있는가
- 대중교통 접근성이 충분한가

이러한 정보는 현재 여러 기관·포털에 흩어져 있어, **실제로 살아보기 전까지는 파악하기 어렵다**는 것이 본 프로젝트의 문제의식이다. 특히 자취 경험이 없는 대학생·사회초년생일수록 이 정보 비대칭으로 인해 불편이나 위험을 사후에 겪는 경우가 많다.

## 2. 프로젝트 목적 및 목표

**목적:** 주소 하나만 입력하면 해당 지역의 안전·생활편의·교통 접근성을 종합 점수화하여 보여주는 "동네 성적표" 서비스를 제공한다.

**목표**
1. 부산 사상구(1차 프로토타입 범위) 내 임의 주소에 대해 정량화된 진단 리포트 제공
2. 기존 부동산 서비스가 다루지 않는 비(非)금전적 정주 여건 정보를 시각화
3. 팀 프로젝트 범위 내에서 구현 가능한 수준으로 데이터·기능 스코프를 명확히 한정
4. 사용자마다 다른 니즈(1인 가구 vs 어린 자녀가 있는 다인 가구 등)를 기본값 + 옵션 방식으로 반영

## 3. 기존 서비스와의 차별점

| 구분 | 기존 서비스 (직방/다방 등) | 동네 진단 |
|---|---|---|
| 제공 정보 | 시세, 매물 사진, 평형 | 안전·생활편의·교통 종합 점수 |
| 데이터 성격 | 거래 정보 | 공공데이터 기반 정주 여건 |
| 의사결정 시점 | 매물 선택 이후 | 지역 선택 이전 사전 진단 |

## 4. 활용 데이터 및 수집 방안

**1차 프로토타입 범위를 부산광역시 사상구 한 곳으로 한정**한다 (지역 확장은 프로토타입 검증 이후 과제). 이에 따라 각 지표의 데이터도 "사상구 단위로 의미 있게 쓸 수 있는가"를 기준으로 재검토 중이며, 아래는 확정 목록이 아니라 **팀원별로 조사한 후보 목록**이다. 실제 컬럼 구성·갱신 주기·사상구 단위 제공 여부를 확인한 뒤 최종 채택 여부를 결정한다.

> 예: 기존에 채택했던 "경찰서별 5대 범죄 발생 현황"은 부산 전체 16개 경찰서 단위 데이터라, 사상구 하나만 보는 프로토타입에서는 활용도가 낮을 수 있어 재검토가 필요하다.

**생활 인프라 후보**
- 건강보험심사평가원_병원정보서비스 API
- 소상공인시장진흥공단_상가(상권)정보 API
- 부산광역시_악취 및 VOCs 측정망 API
- 부산교통공사_소음 측정 정보_GW API
- 부산광역시_사상구 어린이집 현황 API (어린 자녀가 있는 가구 고려)
- 부산광역시_어린이 보호구역 내 사고이력정보 API

**안전 인프라 후보**
- 부산광역시_CCTV설치 현황 정보 API
- 부산광역시경찰청_경찰서별 5대 범죄 현황 API (사상구 단위 프로토타입에서는 활용도 재검토 필요)
- 부산광역시_주요 하천 수위 정보 API (재난안전)
- 부산광역시_교통사고 다발지역 정보 API

**교통 인프라 후보**
- 국토교통부(TAGO)_버스위치정보 / 버스정류소정보 / 버스노선정보 / 버스도착정보 API
- 국토교통부(TAGO)_고속버스정보 / 고속버스도착정보 / 시외버스정보 API
- 국토교통부(TAGO)_국내선박운항정보 / 국내항공운항정보 API
- 국토교통부(TAGO)_지하철정보 / 열차정보 API

**주소 → 좌표 변환**
- 카카오맵 지오코딩 REST API

**부산빅데이터웨이브 후보**
- 부산광역시_노인교실 현황(노인복지) CSV
- 부산광역시_신호등 현황 API
- 부산광역시_부산버스정보시스템 API
- 부산광역시_사고위험지역 현황 CSV
- 부산광역시_과거 산사태 정보 API

> 위 목록 외에도 팀원 각자 활용 가능한 데이터를 추가로 조사한다. 데이터 확정 후 전처리(정제) 방법 논의로 이어간다.

## 4-1. 사용자 세그먼트별 니즈 대응 전략

**문제의식**: 같은 주소에 대한 진단 결과가 모든 사용자에게 동일하게 만족스러울 수 없다. 예를 들어 1인 가구 사용자에게는 만족스러운 결과(예: 100점)가, 어린 자녀를 키우는 다인 가구 사용자에게는 주변 보육시설 부재 등의 이유로 납득되지 않을 수 있다.

**해결 방향**
1. **기본값**: 안전·생활편의·교통이라는 가장 기본적인 니즈로 산출한 점수를 기본 결과로 제공한다.
2. **옵션 선택**: 사용자가 진단 전에 가구 특성(어린 자녀 동반, 노인 동거 등)을 선택할 수 있게 한다.
3. **가중 반영**: 선택된 옵션에 따라 기본 공식에 해당 변수(어린이집·보육시설 밀도, 요양시설 밀도 등)를 추가로 반영해 재계산한다.

## 4-2. 팀 학습 우선순위

- **데이터 담당, 백엔드 담당**: CSV·JSON 기본 개념 → Python 기본 문법과 라이브러리(pandas, os, requests, pathlib, sqlalchemy, FastAPI) → 지오코딩·API 호출·전처리 순으로 학습한다.
- **프론트엔드 담당**: 현재 단계에서는 화면 구현보다 아이디어 구체화와 React·Tailwind CSS 학습에 우선순위를 둔다.

## 5. 시스템 구성 개요

```
[사용자] → 주소 입력
    ↓
[프론트엔드] 주소 검색 UI → 지오코딩 API 호출
    ↓
[백엔드] 좌표 기반으로 안전/편의/교통 점수 DB 조회 및 연산
    ↓
[점수화 엔진] 각 지표 정규화 → 가중합으로 종합 점수 산출
    ↓
[프론트엔드] 동네 성적표 리포트 화면 렌더링
```

**핵심 기능**
- 주소 검색 및 좌표 변환
- 구·동 단위 안전/편의/교통 지표 조회
- 정규화 및 가중치 기반 종합 점수 산출
- 점수 시각화 리포트 (레이더 차트 또는 점수 카드)
- (확장 기능) 두 지역 비교, 즐겨찾기 저장

## 6. 기술 스택

| 영역 | 기술 | 비고 |
|---|---|---|
| 프론트엔드 | React (Vite) + Tailwind CSS | 컴포넌트 단위 분업에 유리 |
| 시각화/지도 | Recharts, 카카오맵 JavaScript SDK | 점수 차트 및 주소 검색·지도 표시 |
| 백엔드 | Python + FastAPI | 데이터 전처리(pandas)와 언어 통일, 궁합 좋음 |
| 데이터베이스 | Turso (libSQL 클라우드) | SQLite 기반이라 가볍고, 클라우드 서버 관리 부담 없이 팀 전체가 공유 |
| 데이터 전처리 | Python + pandas | 공공데이터 정제 및 점수화 로직 구현 |
| 배포 | 프론트: Vercel/Netlify, 백엔드: Render/Railway | 무료 티어로 학기 프로젝트 충분 |
| 협업 도구 | GitHub, Notion/Figma | 이슈·PR 관리, 화면 설계 공유 |

**데이터 처리 파이프라인**
```
공공데이터(CSV/API) → Python/pandas 전처리 & 점수화 → Turso(libSQL) 적재
→ FastAPI REST API → React 프론트엔드 조회 및 시각화
```

## 9. 기대 효과

- 자취방·이사를 준비하는 사용자에게 기존 부동산 서비스가 제공하지 않는 정주 여건 정보를 제공
- 공공데이터를 실생활 문제 해결에 접목한 사례로서 데이터 활용 역량 입증
- 확장 시 타 지역(수도권 등) 적용 및 소음·재난안전 등 추가 지표 결합 가능

## 10. 리스크 및 대응 방안

| 리스크 | 대응 방안 |
|---|---|
| 데이터 단위 불일치 (경찰서 관할 ≠ 행정동 경계) | 관할구역-행정동 매핑 기준을 팀 내 사전 정의 |
| 지오코딩 API 호출량 제한 | 배치 처리 및 캐싱으로 호출 횟수 최소화 |
| 소음 데이터 부재로 인한 지표 공백 | 1차 버전에서 제외, 향후 확장 과제로 명시 |
| 일정 지연 | 핵심 기능(안전+편의+교통) 우선 구현, 비교 기능 등은 스트레치 골로 분리 |
